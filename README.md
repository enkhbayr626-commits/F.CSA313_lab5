# Lab05 — API систем тест Postman ба Newman

**Хичээл:** F.CSA313 — Программ хангамжийн чанарын баталгаа ба тест (2026)

**Оюутан:** С. Энхбаяр

## Ажлын орчин

API сервер болон Newman-ийг WSL2 Ubuntu дотор ажиллуулна. Багшийн өгсөн API кодыг өөрчлөлтгүйгээр `server.js` нэрээр хадгалсан. Сервер нэмэлт npm сан шаарддаггүй, өгөгдлийг санах ойд хадгална.

Бодитоор шалгасан орчны хувилбарууд:

```text
$ node -v
v18.19.1
$ newman -v
6.2.3
$ git --version
git version 2.43.0
```

Newman-ийг хэрэглэгчийн эрхээр суулгах:

```bash
npm install --prefix ~/.local --global newman@6
export PATH="$HOME/.local/bin:$PATH"
newman -v
```

`export PATH` командыг шинэ терминал бүрд ажиллуулна, эсвэл `~/.bashrc` файлдаа нэмнэ.

## Ажиллуулах

WSL Ubuntu-ийн эхний терминалд:

```bash
cd ~/projects/F.CSA313_lab5
node server.js
```

Серверийн хаяг: `http://localhost:3000`. Өөр WSL терминалд:

```bash
cd ~/projects/F.CSA313_lab5
export PATH="$HOME/.local/bin:$PATH"
newman run lab05-collection.json --color off
echo "exit=$?"
```

Collection нь Postman Collection v2.1 JSON форматтай. Postman-д Import → файл сонгож оруулна. Collection variable `baseUrl` нь `http://localhost:3000`; JSON body-той хүсэлтүүд `Content-Type: application/json` header ашиглана.

## Тест дизайн

### Бие даан тестлэгдэх функц

Тестлэх функц нь `POST /registrations`: `studentID`, `courseID` оролтоор оюутны төлөв, хичээл байгаа эсэх, урьдач нөхцөлийг шалгаж бүртгэл үүсгэнэ. `PUT /students/:id`, `PUT /courses/:id` нь кейсийн эхний өгөгдлийг бэлдэх setup хүсэлтүүд юм.

Тест дизайны таван алхмыг дараах байдлаар хэрэглэнэ:

| Алхам | Энэ API-д хэрэглэх нь |
|---|---|
| 1. Бие даан тестлэгдэх функц | Хичээлд бүртгүүлэх `POST /registrations` |
| 2. Сонголтууд | Оюутан, үзсэн хичээл, хичээлийн оршин байдал, урьдач нөхцөл, хүсэлтийн формат |
| 3. Төлөөлөх утгууд | Доорх эквивалент ангиудаас `active`, `inactive`, байхгүй ID, хоосон болон хэсэгчилсэн массив сонгох |
| 4. Спецификаци | TC01–TC12 нөхцөл бүрд хүлээгдэх статус, `result`, шаардлагатай `missing` утгыг тогтоох |
| 5. Бодит тест кейс | TC01–TC12-ыг өөрийн setup PUT, POST, тусдаа статус ба утгын oracle-тай Postman folder болгон хэрэгжүүлсэн |

### Сонголт ба төлөөлөх утгууд

### Спецификацийн хүснэгт

TC01 нь `B232270153`, `CS313` ID ашиглана. Бусад кейсийн ID нь `B232270153_TCnn`, `CS313_TCnn` байна; жишээлбэл TC02-д `B232270153_TC02`, `CS313_TC02`. Ингэснээр кейсүүдийн setup өгөгдөл давхцахгүй. Хүснэгтийн `—` нь тухайн бичлэгийг үүсгэхгүй, тухайн массивыг үнэлэх боломжгүй гэсэн утгатай.

| Кейс | Ангилал ба нөхцөл | Оюутны setup | `coursesTaken` | Хичээлийн setup / `prerequisites` | Статус | `result` | Нэмэлт хүлээлт |
|---|---|---|---|---|---:|---|---|
| TC01 | Happy path, бүх урьдач нөхцөл хангасан | `active` | `["CS201"]` | `["CS201"]` | 201 | `OK` | `registrationID` тоо |
| TC02 | Оюутан байхгүй | Үүсгэхгүй | — | `["CS201"]` | 200 | `ERROR_NO_STUDENT` | — |
| TC03 | Оюутан идэвхгүй | `inactive` | `["CS201"]` | `["CS201"]` | 200 | `ERROR_INACTIVE_STUDENT` | — |
| TC04 | Хичээл байхгүй | `active` | `["CS201"]` | Үүсгэхгүй | 200 | `ERROR_NO_COURSE` | — |
| TC05 | Урьдач нөхцөлийг огт хангаагүй, үзсэн хичээлгүй | `active` | `[]` | `["CS201","CS202"]` | 200 | `ERROR_PREREQUISITES` | `missing=["CS201","CS202"]` |
| TC06 | Урьдач нөхцөлийг хэсэгчлэн хангасан | `active` | `["CS201"]` | `["CS201","CS202"]` | 200 | `ERROR_PREREQUISITES` | `missing=["CS202"]` |
| TC07 | Давхар алдаа, оюутан ба хичээл хоёулаа байхгүй | Үүсгэхгүй | — | Үүсгэхгүй | 200 | `ERROR_NO_STUDENT` | Оюутны алдаа түрүүлнэ |
| TC08 | Давхар алдаа, идэвхгүй оюутан ба байхгүй хичээл | `inactive` | `["CS201"]` | Үүсгэхгүй | 200 | `ERROR_INACTIVE_STUDENT` | Идэвхгүй төлөвийн алдаа түрүүлнэ |
| TC09 | Хязгаарын нөхцөл, урьдач нөхцөлгүй хичээл | `active` | `[]` | `[]` | 201 | `OK` | `registrationID` тоо |
| TC10 | Форматын алдаа, `studentID` талбар дутуу | `active` | `["CS201"]` | `["CS201"]` | 400 | `ERROR_BAD_REQUEST` | POST body зөвхөн `courseID`-тай |
| TC11 | Форматын алдаа, `courseID` талбар дутуу | `active` | `["CS201"]` | `["CS201"]` | 400 | `ERROR_BAD_REQUEST` | POST body зөвхөн `studentID`-тай |
| TC12 | Форматын алдаа, буруу JSON | `active` | `["CS201"]` | `["CS201"]` | 400 | `ERROR_BAD_JSON` | Raw body: `{"studentID":` |

TC01–TC09-ийн POST body нь тухайн кейсийн хоёр ID-тай JSON объект байна. TC10, TC11-д зөвхөн хүснэгтэд заасан талбарыг орхино; TC12-д raw body-г синтаксын алдаатайгаар илгээнэ. Бүх кейс өөрт шаардлагатай бичлэгээ өөрөө PUT-ээр үүсгэнэ. TC07-д хоёр бичлэгийг зориуд үүсгэхгүй; бусад кейс энэ хоёр ID-г ашиглахгүй. Байхгүй бичлэгүүдийг урьд нь үүсгэж болохгүй: серверт DELETE endpoint байхгүй.

### Oracle ба давхар алдааны дараалал

POST хүсэлт бүрд хүлээгдэх HTTP статус болон `result` утгыг тусдаа `pm.test`-ээр шалгана. TC01, TC09-д `registrationID` нь тоо эсэхийг шалгах бөгөөд яг `1` эсвэл `2` байхыг шаардахгүй. TC05, TC06-д `missing` массивыг хүснэгтийн утгатай харьцуулна. Амжилтгүй бизнес нөхцөлд API `200` болон `ERROR_*` буцаадаг тул зөвхөн статус шалгах нь хангалтгүй.

Серверийн кодоос тогтоосон дараалал нь: JSON parsing → шаардлагатай талбарууд → оюутан байгаа эсэх → идэвхтэй эсэх → хичээл байгаа эсэх → урьдач нөхцөл. TC07, TC08-ыг Newman-аар ажиллуулж, оюутан байхгүй болон идэвхгүй төлөвийн алдаа хичээл байхгүй алдаанаас түрүүлж буцдагийг баталгаажуулсан.

### Боломжгүй болон утгагүй хослолууд

- Байхгүй оюутанд `active`/`inactive` төлөв, үзсэн хичээлийн жагсаалт оноох боломжгүй; тэдгээрийг үнэлэхээс өмнө `ERROR_NO_STUDENT` буцна.
- Байхгүй хичээлийн урьдач нөхцөлийг үнэлэх боломжгүй; идэвхтэй оюутны хувьд `ERROR_NO_COURSE` буцна.
- Урьдач нөхцөлгүй хичээлд нөхцөл дутуу байх боломжгүй; хоосон `coursesTaken` нь энэ тохиолдолд амжилттай бүртгэлд саад болохгүй.
- Ганц урьдач нөхцөлтэй хичээлд "заримыг үзсэн" анги үүсэхгүй; TC06-д хоёр урьдач нөхцөл авч нэгийг нь хангасан.
- Идэвхгүй оюутны урьдач нөхцөл дутуу байсан ч уг алдаа тусдаа буцахгүй; идэвхтэй эсэхийн шалгалт түрүүлнэ.

## Анхны кейс ба oracle

`TC01 — Урьдач нөхцөл хангасан идэвхтэй оюутан` folder дарааллаар гурван хүсэлт ажиллуулна:

1. `PUT /students/B232270153`: `status=active`, `coursesTaken=["CS201"]`.
2. `PUT /courses/CS313`: `prerequisites=["CS201"]`.
3. `POST /registrations`: `studentID=B232270153`, `courseID=CS313`.

POST хүсэлтэд гурван `pm.test` oracle байна: HTTP статус `201`, хариуны `result` утга `OK`, `registrationID` тоо эсэх. `registrationID`-ийн тогтмол утгыг шалгахгүй. Setup PUT бүрд статус `200`, `result=OK` гэсэн хоёр oracle байна. Кейс өөрийн setup-аа гүйцэтгэдэг тул дахин ажиллуулах боломжтой.

## Бие даасан collection

`lab05-collection.json` нь TC01–TC12 гэсэн 12 локал folder болон `Public API` folder-той. Кейсүүд өөрийн оюутан, хичээлийн ID ашигладаг тул өөр кейсийн setup өгөгдөлд тулгуурлахгүй. TC07-д байхгүй хоёр ID-г зориуд үүсгэхгүй. Буруу JSON илгээх TC12-ийн body нь raw `{"studentID":` байна.

Локал хэсэгт 19 setup PUT хүсэлт, 12 POST хүсэлт, нийт 31 хүсэлт болон 66 assertion байна. Setup oracle 38, POST статус ба result oracle 24, амжилттай хоёр бүртгэлийн ID oracle 2, `missing` массивын oracle 2 байна. Кейсийн тоо нь assertion-ы тоотой адил биш.

Нэг кейсийг тусад нь ажиллуулах жишээ:

```bash
newman run lab05-collection.json --folder "TC06 — Урьдач нөхцөлийг хэсэгчлэн хангасан" --color off
```

## Нийтийн API тест

`Public API` folder нь `GET https://jsonplaceholder.typicode.com/users` хүсэлттэй. Гурван oracle: HTTP статус `200`, хариу JSON массив, эхний хэрэглэгчийн `name="Leanne Graham"`. Тусад нь ажиллуулах:

Нийтийн GET API нь өөрийн API-тай харьцуулахад setup өгөгдөл үүсгэх шаардлагагүй тул хялбар боловч интернет болон гаднын үйлчилгээний төлөвөөс хамаардаг тул орчныг бүрэн удирдах нь хэцүү.
